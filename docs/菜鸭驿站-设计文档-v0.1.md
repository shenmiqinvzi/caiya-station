## 1. 一句话定位

玩家在仓库区/农场镇找到随机出现的“菜鸭驿站”，把背包里带不走或不敢带的物品寄回地堡马蜂自提点；驿站收费、可能丢件，可花钱和稀有物品请护送队降低丢件率。每个驿站每局只能用一次。

它解决的不是“走路慢”，而是**搜打撤里最常见的两件事：包满了，以及带着贵重货不敢继续冒险**。

## 2. 目标与非目标

### 2.1 目标

- 给玩家一个**把溢出物资变成已送达货物**的渠道，腾出格子/负重，继续搜刮或轻装撤离。
- 让“寄”与“不寄”成为一次真实的成本/风险决策，而不是纯收益 buff。
- 与游戏既有系统贴合：马蜂自提点、现金/金钱、虚化的羽毛、狗牌、快递主题。
- 失败可解释、可恢复；不复制物品、不静默吞物品。
- 单局最多 1–2 次寄送，不能替代撤离，不能把死亡惩罚抹平。

### 2.2 非目标

- 不做共享单车/租赁/骑行。
- 不做联机。
- 不做独立的基地领取界面；直接复用马蜂自提点的到货缓冲区。
- 不做驿站库存、升级、声望、保险、拍卖。
- 零号区不设驿站。
- **不修改护送队价格与所需物品**（用户已定）：
  - 拾荒者团：1000 金钱/现金 + 4 个「虚化的羽毛」。
  - 雇佣兵团：2000 金钱/现金 + 4 个「狗牌」。
- 不做“把所有家当一次性寄走”的无上限搬运。

## 3. 核心循环

1. 进入仓库区或农场镇，地图上出现菜鸭驿站标记，进入时有一次公告提示。
2. 找到驿站，交互打开寄送面板。
3. 从**背包**里选物品；受 12 格 / 25kg 上限约束。
4. 选择是否请护送队；面板显示运费、基础损耗、护送后损耗、预计总成本。
5. 确认：扣运费/护送费与物品 → 结算丢件 → 幸存物品进入马蜂自提点到货缓冲区 → 驿站关闭（本局该站不可再用）。
6. 玩家继续搜刮或撤离；回地堡后在马蜂自提点领取。
7. 若玩家死亡，已送达物品仍在自提点；未寄出的背包物品按原游戏规则处理。

## 4. 玩家价值与使用场景

### 4.1 什么时候值得用

- 背包已满，但前方还有高价值物资。
- 身上带着一批高价货，准备打 boss、穿危险区或走远路撤离。
- 负重/格子吃紧，想轻装继续搜。
- 离撤离点远，带着全部家当死亡损失太大。

### 4.2 什么时候不值得用

- 就在撤离点旁边，直接带出去更划算。
- 货物价值太低，最低运费 200 已经超过收益。
- 驿站不在路线上，或本局已经用过。
- 运费 + 期望损耗 + 护送成本高于玩家对死亡/绕路风险的估计。

### 4.3 设计边界

- 它是**溢出物资的保险/快递**，不是“所有物资的免费仓库”。
- 12 格 / 25kg 的单次上限 + 每站每局一次，保证它不能把一整局家当搬空。
- 死亡后已送达物品安全，这是它的核心价值；因此运费和损耗必须真实存在。

## 5. 站点

### 5.1 数量与分布（每局）

| 地图 | 驿站数量 |
| --- | --- |
| 零号区 | 0 |
| 仓库区 | 1 |
| 农场镇 | 2 |

- “每局”指一次 raid；同一局内离开再进入同一地图，**不重 roll、不重置使用状态**。
- 新的一局重新随机位置与使用状态。
- 零号区没有驿站；在地堡放一个说明终端/告示，并在首次进入仓库区/农场镇时给一次公告，避免玩家不知道系统存在。

### 5.2 随机与位置约束

- 每张地图准备一组**候选锚点**（现有地标、道路节点、安全空地），每局从中随机选 1/2 个。
- 硬约束：
  - NavMesh 可达，地面坡度 ≤ 35°，能放下驿站模型与交互范围。
  - 不在水里、不在锁门/不可返回区域、不在撤离倒计时区内。
  - 与任意撤离点/CountDownArea 的距离 **40–80 米**（“离撤离点远一点”，但不做成长途跋涉）。
  - 与其它驿站、原生传送点、POI 至少 15 米，避免交互提示互相抢。
  - 从玩家出生点/AI 路径可达；校验失败重试，最终回退到该地图的固定安全锚点。
- 同一局的位置写入存档；读档、重进地图不变化。新 raid 重新生成。

### 5.3 可发现性

- 地图标记：绿色/黄色驿站图标，名称“菜鸭驿站”。
- 屏幕标签：80 米内显示“菜鸭驿站 N米”。
- 进入地图时公告一次：“菜鸭驿站在本区域营业，地图已标记。”
- 驿站模型：小亭/柜台 + 绿色招牌 + 鸭头标志；未使用时招牌亮，使用后变灰/落闸。
- 交互提示与站点名称清晰，不与原生传送点/撤离点重叠（位置约束 + 提示让位规则）。

### 5.4 一次性

- 每个驿站每局只能成功发货一次。
- 发货成功后：标记 `Used`，关闭交互，视觉变为停业。
- 发货在扣费/扣物品之前失败：不消耗站点，可重试。
- 发货已送达但存档写入失败：以“已送达”为准，重试写状态；不能再次发货。

## 6. 可寄送物品与上限

### 6.1 来源

- 只允许**玩家背包内**的物品。
- 不包含：装备栏、快捷栏、基地仓库、宠物背包、地面容器。
- 没有背包时不能寄送，提示“需要背包”。

### 6.2 上限

- 单次最多 **12 格** 或 **25kg**，先到先算。
- “格”按选中的物品堆叠数计算；一个堆叠占 1 格。
- 重量按物品实际 `TotalWeight` 计算。
- 上限在面板实时显示，超出时禁止确认。

### 6.3 排除项

以下物品不可选：

- 任务物品、任务快递箱（`Item_Quest_DeliverBox_*`）。
- 钥匙、门禁卡、唯一/剧情物品。
- 现金/货币类物品。
- 已装备物品。
- 容器类物品（背包、箱子、袋子等）第一版不寄；容器内容不展开选择，避免“丢容器连带一包东西”。
- 价值为 0 且无实际用途的物品：允许选，但面板提示“运费高于货值”。

实现时以**物品元数据标签/名称/类型 + 配置黑名单**共同判断；不能只靠 `CanDrop`。任务/唯一物品必须在代码与测试中显式保护。

## 7. 计价

### 7.1 货值

`V = Σ(max(1, item.Value) × item.StackCount)`，只统计可寄物品。

### 7.2 运费

```
fee = clamp(round(V × 0.10), 200, 5000)
```

- 10% 货值，最低 200，最高 5000（用户已确认）。
- 运费在发货时一次性扣除，不退还。
- 支付方式：**金钱（ATM 余额）或现金**，由 `EconomyManager.Pay` 同时支持；面板显示两种余额。
- 运费不足时禁止发货；不做赊账。

### 7.3 示例

| 货值 V | 运费 |
| --- | --- |
| 2,000 | 200 |
| 10,000 | 1,000 |
| 30,000 | 3,000 |
| 50,000 | 5,000 |
| 100,000 | 5,000（封顶） |

## 8. 损耗

### 8.1 基础损耗率

按货值分档：

| 货值 V | 基础损耗率 L0 |
| --- | --- |
| ≤ 2,000 | 5% |
| 2,001–10,000 | 8% |
| 10,001–30,000 | 12% |
| > 30,000 | 15% |

- 损耗率上限 20%（当前档位最高 15%，留出后续调整空间）。
- 损耗率是**期望值**，实际按件随机，面板必须提前给出区间/上限，不能盲赌。

### 8.2 护送后的损耗率

| 护送 | 损耗率 |
| --- | --- |
| 无 | L0 |
| 拾荒者团 | max(2%, L0 × 0.6) |
| 雇佣兵团 | max(2%, L0 × 0.3) |

- 护送队价格与物品**固定，不调整**：
  - 拾荒者团：1000 金钱/现金 + 4 个「虚化的羽毛」。
  - 雇佣兵团：2000 金钱/现金 + 4 个「狗牌」。
- 每单最多选一队；费用与运费合并为一次支付。
- 若玩家不足，选项置灰并说明缺什么。
- 低价值单子请护送会明显不划算；面板提示“护送费高于货值”，但不禁止。

### 8.3 丢件结算

1. 对每个选中的**堆叠**独立掷一次：`Random < L` 记为候选丢失。
2. 约束：
   - 最多丢失 `max(1, floor(选中堆叠数 × 0.30))` 个堆叠。
   - 丢失总价值不超过 `V × 0.50`。
   - 选中堆叠 ≥ 2 时，至少保留 1 个堆叠。
   - 选中堆叠 = 1 时，允许该件以概率 L 全损；面板显式警告“单件寄送可能全损”。
3. 超出约束的候选按随机顺序剔除；留下的候选即实际丢失。
4. 丢失物品直接销毁（连同其内部树）；幸存物品进入送达流程。
5. 结果写入回执：丢失物品名、数量、价值；送达物品；运费；护送；总损失。

### 8.4 为什么这样定

- 损耗率随货值上升，体现“越值钱越容易被盯上”，但有 20% 上限，不会出现“寄得越贵越亏到不敢寄”。
- 按堆叠独立掷、再设件数/价值上限，期望损失接近 L × V，最坏情况被限制在 50% 价值/30% 件数以内。
- 单件全损是例外，但面板提前警告，且可以请护送把概率压到 2%–4.5%。
- 不按“最贵物品优先丢”，避免玩家觉得系统专挑好东西；也不做“最便宜优先”，避免高价值单子靠塞垃圾规避风险。

### 8.5 回执

发货后立即显示一次回执，并写入模组历史：

```
菜鸭驿站 · 发货回执
送达：马蜂自提点
货物：8 件 / 价值 12,400
运费：1,240
护送：拾荒者团（损耗 4.8%）
丢失：2 件 / 价值 610
   - 罐头 x3
   - 布条 x5
送达：6 件 / 价值 11,790
```

回执只用于查账与叙事，不参与结算。丢失原因用一句随机风味文本（遭遇拾荒者/雇佣兵/风暴等），不改变数值。

## 9. 发货、送达与领取

### 9.1 发货

- 在驿站面板确认后：
  1. 再次校验背包、上限、费用、护送物品、站点未使用。
  2. 扣运费 + 护送费/物品（一次 `Cost`）。
  3. 结算丢件；销毁丢失物品。
  4. 幸存物品逐件 `PlayerStorage.Push(item, true)` → 进入马蜂自提点到货缓冲区。
  5. 标记站点已用；写回执与状态；关闭面板；驿站停业。
- `PlayerStorage.Push(item, true)` 会把物品转成 `ItemTreeData` 加入 `IncomingItemBuffer`，原物品 detach/destroy；**不需要自建物品序列化/重建**。
- 发货时玩家可能不在基地；`Push(..., true)` 直接写缓冲区，不需要基地实例，这正是它能工作的关键。

### 9.2 送达

- 立即送达（写入缓冲区），不设运输时间。
- 玩家回地堡后，在马蜂自提点看到到货；用原生领取流程取走。
- 到货与任务奖励共用同一个缓冲区；模组额外弹一次“菜鸭驿站：N 件已送达”提示，并在驿站回执/基地公告中说明，避免玩家误以为是任务物品。

### 9.3 领取

- 复用马蜂自提点原生领取；不另做领取界面。
- 玩家背包/仓库满时，物品留在缓冲区，不会丢失。
- 若缓冲区异常，提供诊断信息；不自动删除。

## 10. 护送队

| 队伍 | 费用 | 效果 | 说明 |
| --- | --- | --- | --- |
| 拾荒者团 | 1000 金钱/现金 + 4 虚化的羽毛 | 损耗 ×0.6，下限 2% | 便宜，效果中等 |
| 雇佣兵团 | 2000 金钱/现金 + 4 狗牌 | 损耗 ×0.3，下限 2% | 贵，效果最好 |

- 价格与物品**按用户设定固定**，设计/实现都不得擅自调整。
- 每单最多一队；可与运费合并支付。
- 护送只影响损耗率，不影响运费、上限、站点次数。
- 护送失败/不足时不允许“先发货后补”；必须一次付清。
- 若玩家只有金钱没有现金，或只有现金没有金钱，都允许；由原生支付同时支持。
- 护送物品从背包扣除；若放在基地仓库，不算携带，面板提示“需要随身携带”。

## 11. 界面与反馈

### 11.1 驿站面板

一个居中的面板，避免压住原生右侧栏：

- 标题：菜鸭驿站｜本局剩余可用：是/已停业
- 背包物品列表：名称、数量、单件价值、总价值、重量、复选框。
- 顶部/底部固定信息：
  - 已选：N 格 / 12 格，W kg / 25 kg，总价值 V。
  - 运费：F；基础损耗：L0（约 X 元）。
  - 护送：无 / 拾荒者（L1，费用）/ 雇佣兵（L2，费用）。
  - 预计总成本：运费 + 期望损耗 + 护送费；明确“实际按件随机，最多丢 30% 件数/50% 价值”。
- 按钮：全选可寄、清空、确认发货、关闭。
- 不可确认的原因要写明：超格/超重、无物品、钱不够、护送物品不够、站点已用、缓冲区不可用。

### 11.2 发货后

- 回执面板（可关闭）。
- 屏幕提示：“已发货 N 件，丢失 M 件；请回地堡马蜂自提点领取。”
- 驿站视觉停业；地图图标变灰。

### 11.3 公告与引导

- 首次进入仓库区/农场镇：一次公告“菜鸭驿站在本区域营业，地图已标记”。
- 地堡说明终端/告示：解释服务、上限、损耗、护送、领取地点。
- 零号区没有驿站；公告中说明“零号区暂未开通”。

## 12. 持久化与失败恢复

### 12.1 存档键（新命名空间）

建议三个键，均为 JSON 字符串，放原生存档：

- `CaiYaStation.State.v1`：存档 ID、当前 raid token、设置快照、发货日志状态。
- `CaiYaStation.World.v1`：本局驿站布局（地图、场景、坐标、朝向、是否已用、锚点 ID）。
- `CaiYaStation.Receipts.v1`：回执历史（送达/丢失/费用/护送），仅查账与展示。

不读取旧 `DuckovSharedBike.*` 键；旧键保留不动。

### 12.2 Raid 状态

- 每个 raid 一个 `RaidToken`；同一 token 内驿站布局与使用状态不变。
- 新 raid（从地堡进入/死亡后重开）生成新 token，重新随机。
- 读档、重进同一地图不重 roll。
- 实现上用 `LevelManager.IsRaidMap` + 场景切换/死亡/撤离事件判断；若不可靠，退化为“从基地进入 raid 场景时生成新 token”，并在测试中验证。

### 12.3 发货事务

发货不是单一原子操作（扣费、销毁、推送、写状态），必须有发货日志与恢复顺序：

1. 生成 `ShipmentId`，写入 `Prepared`（选中物品、费用、护送、损耗计划）。
2. 扣费/扣护送物品；失败则回到 `Prepared`，不发货物。
3. 结算丢件、销毁丢失物品。
4. 逐件推送幸存物品；每推一件记 `DeliveredItemIds`。
5. 标记站点 `Used`，写 `Delivered` 与回执。

恢复原则：

- 已推送的物品在原生缓冲区，不会因模组存档失败而丢。
- 若第 3/4 步中断：加载时按日志继续推送未推送的幸存物品；已推送的不重复。
- 若第 5 步中断：物品已送达，重试把站点标记为已用；不允许再次发货。
- 若第 2 步扣费成功但第 4 步完全失败：优先重试发货；无法恢复时给玩家回执/客服补偿方案，不静默吞货。
- **永不复制**：每件物品推送前记录实例 ID；已推送的不得再次推送。
- **永不静默销毁**：丢失物品必须在回执中列出。

### 12.4 物品保护

- 任务/钥匙/唯一物品在 UI 层不可选，在结算层再次过滤。
- 若物品在选中后、发货前变成任务物品/被装备，发货前重新校验并剔除或中止。
- 容器不参与第一版；后续版本若要支持，必须单独设计内部物品损失规则。

## 13. 技术方案

### 13.1 原生接口（已核对）

| 用途 | 接口 |
| --- | --- |
| 送达缓冲区 | `PlayerStorage.Push(Item item, bool toBufferDirectly=true)`；`PlayerStorage.IncomingItemBuffer`；`PlayerStorageBuffer` |
| 领取 | 原生马蜂自提点 `PlayerStorage.TakeBufferItem(int)` |
| 支付 | `EconomyManager.Pay(Cost cost, bool accountAvaliable, bool cashAvaliable)`；`EconomyManager.Money` / `Cash` |
| 费用/物品成本 | `Duckov.Economy.Cost(long money, (int id, long amount)[] items)` |
| 估值 | `Item.Value`、`Item.StackCount`、`Item.TotalWeight` |
| 物品操作 | `Item.Detach()`、`Item.DestroyTree()`、`Inventory.RemoveItem/RemoveAt`、`Inventory.Content` |
| 背包 | 玩家角色物品的背包槽 `Inventory`；实现前先做 spike |
| 驿站交互/标记 | `InteractableBase`、`SimplePointOfInterest`、`SafeGround`/NavMesh |
| Raid 判断 | `LevelManager.IsRaidMap`、场景切换/死亡/撤离事件 |

关键结论：**送达不需要自建物品序列化**。`PlayerStorage.Push(..., true)` 已经把物品转成 `ItemTreeData` 放入原生缓冲区，物品实例、堆叠、耐久、附件都由原生保存。

### 13.2 工程结构

新工作空间建议：

```text
CaiYaStation/
  src/CaiYaStation/                 # Unity 模组层（Harmony、交互、UI、世界）
  src/CaiYaStation.Domain/          # 纯逻辑：计价、损耗、护送、上限、回执
  tests/CaiYaStation.Domain.Tests/  # 纯逻辑测试
  mod/                              # info.ini、README、预览图、锚点配置
  scripts/                          # Build/Test/Install
  docs/                             # 设计、施工、安装、验证
  vendor/Harmony/                   # Harmony 2.4.1 + 许可证
  tools/                            # 只读程序集/资源核查
```

- 程序集/模组名：`CaiYaStation`；`info.ini` 的 `name` 必须与加载入口一致；displayName `菜鸭驿站`。
- 目标框架 `netstandard2.1`；引用游戏 Managed 目录与 Harmony。
- 不复制旧租赁引擎、自行车模型、旧存档键。
- 可复用旧工程的：Harmony 加载、`NativeContract` 自检、`SafeGround`/寻位、`SavesSystem` 读写、日志、构建/安装脚本、只读核查工具。

### 13.3 域模型（建议）

- `CourierSettings`：站点数量/上限/费率/损耗档/护送倍率/锚点配置。
- `StationPlan`：站点 ID、地图、场景、坐标、朝向、锚点、已用。
- `ShipmentRequest`：选中物品、总价值、总重量、格数、护送选择。
- `FeeQuote`：运费、护送费、护送物品。
- `LossPlan`：基础率、最终率、候选丢失、实际丢失、总损失。
- `Receipt`：ShipmentId、时间、送达/丢失清单、费用、护送、状态。
- `RaidState`：RaidToken、地图、站点计划、使用状态。
- `ItemEligibility`：可寄/保护规则（纯函数 + 配置）。
- 纯逻辑全部可单测，不依赖 Unity。

### 13.4 失败与并发

- 发货面板打开时禁止重复点击；`_shipping` 标志。
- 驿站使用状态、费用、护送、回执在一次操作中校验；不允许并发发货。
- 只有在地堡/安全场景才允许领取（原生逻辑）；发货在 raid 场景。
- 若 `PlayerStorage` 缓冲区不可用（加载中/异常），禁止发货，不扣费。

## 14. 兼容性

- 与修改背包/仓库/经济/物品的模组可能冲突；测试用户当前 14 个模组（含 `DisplayCashWithMoney`、`ModConfig` 等）。
- 与游戏原生快递任务/快递箱共存：排除 `Item_Quest_DeliverBox_*`；不修改任务状态。
- 与马蜂自提点共存：使用同一下游缓冲区；不删除/重排其它物品。
- Harmony 冲突：使用独立 Harmony ID；只 patch 必要方法；提供 `NativeContract` 自检。
- 不在零号区生成站点；不干扰原生撤离点/传送点。

## 15. 验收标准

### 15.1 垂直切片（必须先过）

1. 仓库区固定生成 1 个驿站，可见、有地图标记、可交互。
2. 选 1 件背包物品，付 200 运费，发货；物品从背包消失。
3. 回地堡马蜂自提点，物品可领取。
4. 读档/重进游戏，物品不复制、不丢失；驿站已用状态保留。
5. 发货后死亡，物品仍在自提点。
6. 运费/护送/损耗/回执数据正确。

### 15.2 完整验收

- 12 格/25kg 上限、超限禁止。
- 运费 10%/最低 200/最高 5000。
- 损耗四档、护送 0.6/0.3、下限 2%、件数/价值上限、单件全损警告。
- 任务/钥匙/唯一/货币/装备/容器不可寄。
- 每站每局一次；新 raid 重新随机；同一 raid 重进不重 roll。
- 随机位置 20 次：可达、离撤离点 40–80m、不重叠、无卡死；失败有回退。
- 费用不足、护送物品不足、缓冲区不可用、重复点击、存档失败等异常路径。
- 与用户当前模组列表共存。

### 15.3 测试分层

- 纯逻辑单测：计价、损耗、上限、保护、回执、RaidState。
- 原生 spike：背包读取、`PlayerStorage.Push`、`EconomyManager.Pay`、Raid 判定。
- 游戏内手工验收：垂直切片 + 完整流程 + 异常恢复。

## 16. 风险与待验证

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 背包 Inventory 访问方式不明确 | 无法选货 | 先做只读 spike，确认槽位与 `Content` |
| `PlayerStorage.Push` 对堆叠/容器/任务物品行为 | 物品异常 | spike + 只读测试 + 排除容器/任务 |
| Raid token 判定不可靠 | 重 roll/状态错 | 用 `IsRaidMap` + 场景事件；测试读档/重进/死亡 |
| 随机位置不可达/卡死 | 系统不可用 | 候选锚点 + 导航/空间校验 + 回退 |
| 费用/发货中断 | 吞货/重复 | 发货日志 + 幂等 + 恢复；先推送再标记使用 |
| UI 复杂/遮挡 | 体验差 | 居中面板；先做最小列表；不做侧栏 |
| 与其它模组冲突 | 崩溃/物品错 | 独立 Harmony ID、NativeContract、兼容测试 |
| 范围过大 | 再次“什么都做了但没验证” | 垂直切片先行，阶段验收 |

## 17. 实施阶段

- **Phase 0（spike，不做完整 UI）**：确认背包读取、`PlayerStorage.Push(...,true)`、`EconomyManager.Pay`、Raid 判定；一个固定驿站、一件物品、发货、领取、读档。
- **Phase 1（最小闭环）**：站点生成/标记/交互；选货；运费；12/25 上限；发货；原生缓冲区；回执；存档。
- **Phase 2（风险与护送）**：损耗、护送、保护规则、单件警告、费用/物品不足。
- **Phase 3（随机与每局状态）**：随机锚点、每站每局一次、RaidToken、公告、基地说明。
- **Phase 4（打磨）**：驿站模型/招牌/停业状态、回执历史、兼容性、完整测试、安装包。

**Phase 0 不通过就不进入 Phase 1**；每次阶段结束必须在游戏内跑一遍，不接受“编译通过就算完成”。
